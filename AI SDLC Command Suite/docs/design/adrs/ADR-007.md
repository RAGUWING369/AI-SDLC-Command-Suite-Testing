# ADR-007: PostgreSQL Full-Text Search for Product Discovery

**Status:** Accepted
**Date:** 2026-05-14
**Deciders:** Full-stack Lead, Backend Developer

---

## Context

ShopNest must satisfy NFR-PE-005: product search P95 response time < 500ms at ≤50,000 products. Product search is the primary buyer discovery mechanism — buyers search by product name, description, and category. The search implementation must:

1. Return ranked results (most relevant first)
2. Handle partial-word queries (e.g., "phone" matches "smartphone")
3. Support category and price range filters combined with text search
4. Scale to 50,000 products without degrading below P95 < 500ms
5. Operate within the $2,000/month AWS budget (CON-001)
6. Be maintainable by a 3-person team with no dedicated search infrastructure ops (CON-003)

The system already uses PostgreSQL 16 on AWS RDS as the primary database (ADR-003). The question is whether native PostgreSQL Full-Text Search is sufficient, or whether a dedicated search service is required.

---

## Decision

**PostgreSQL 16 native Full-Text Search (FTS) using `tsvector` + `tsquery` with a GIN index, implemented via Django ORM `SearchVector`, `SearchQuery`, and `SearchRank`.**

**Implementation:**

```sql
-- tsvector column on products_product
ALTER TABLE products_product
    ADD COLUMN search_vector TSVECTOR;

-- GIN index for fast FTS queries
CREATE INDEX products_product_search_vector_gin
    ON products_product USING GIN (search_vector);

-- Trigger to auto-update search_vector on insert/update
CREATE OR REPLACE FUNCTION products_update_search_vector()
RETURNS TRIGGER AS $$
BEGIN
    NEW.search_vector :=
        setweight(to_tsvector('english', COALESCE(NEW.name, '')), 'A') ||
        setweight(to_tsvector('english', COALESCE(NEW.description, '')), 'B');
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER products_search_vector_update
    BEFORE INSERT OR UPDATE OF name, description
    ON products_product
    FOR EACH ROW EXECUTE FUNCTION products_update_search_vector();
```

**Django ORM query pattern:**

```python
from django.contrib.postgres.search import SearchVector, SearchQuery, SearchRank

def search_products(query: str, category_id=None, min_price=None, max_price=None):
    search_query = SearchQuery(query, config='english')
    qs = Product.objects.filter(
        status='ACTIVE',
        seller__status='ACTIVE',
        seller__subscription__status='ACTIVE',
        search_vector=search_query
    )
    if category_id:
        qs = qs.filter(category_id=category_id)
    if min_price:
        qs = qs.filter(price_paise__gte=min_price)
    if max_price:
        qs = qs.filter(price_paise__lte=max_price)
    return qs.annotate(rank=SearchRank('search_vector', search_query)) \
             .order_by('-rank', '-created_at')
```

**Weight scheme:**
- `'A'` (weight 1.0): product `name` — higher relevance boost
- `'B'` (weight 0.4): product `description` — lower relevance boost

**Caching:**
- Popular search queries (top 100 by frequency in analytics_events) cached in Redis with 1-hour TTL
- Cache invalidated on product create/update via Django post_save signal

---

## Rationale

**PostgreSQL FTS satisfies NFR-PE-005 at MVP scale:**
PostgreSQL GIN-indexed `tsvector` queries at 50,000 rows execute in 20–80ms P95 on a db.t3.small instance (based on PostgreSQL FTS benchmarks at equivalent hardware and record counts). Combined with Redis caching for repeated queries, P95 < 500ms is achievable with significant headroom. An external search service adds operational complexity with no measurable quality improvement at this scale.

**Eliminates a separate search service (CON-001, CON-003):**
Elasticsearch on AWS OpenSearch Service costs ~$150–300/month for a minimum production cluster (2 nodes, m5.large.search). This is 7.5–15% of the $2,000/month budget for a service that serves one feature at MVP scale. Algolia and Typesense SaaS add monthly subscription costs on top of API request fees. PostgreSQL FTS runs on the already-provisioned RDS instance at zero incremental cost.

**Ranking quality is sufficient for MVP:**
PostgreSQL's `ts_rank` function implements TF-IDF-like relevance ranking via the weight scheme. At ≤50,000 products from ≤100 sellers, buyers are unlikely to encounter recall quality problems that require semantic search or synonym expansion. If search NPS falls below target post-launch, the `search_vector` column provides a clean migration path to an external service — `ProductRepo.search()` is the single method to update.

**Upgrade path is non-destructive:**
The `search_vector` column can be backfilled and the trigger retained even after migrating to Elasticsearch — the column simply stops being the query source. Django ORM search query is isolated in `ProductRepo.search()` — changing the backend requires modifying one function, not multiple call sites.

## Alternatives Considered

| Option | Pros | Cons | Why Rejected |
|--------|------|------|-------------|
| AWS OpenSearch (Elasticsearch) | Industry-standard; fuzzy matching; typo tolerance; synonym expansion; faceted search | ~$150–300/month incremental cost; separate cluster to operate; synchronization lag between PostgreSQL and OpenSearch; 3-person team must maintain two data stores | CON-001 (budget); CON-003 (ops burden); overkill at 50K products |
| Algolia | Typo tolerance; real-time indexing; hosted; excellent relevance | ~$100–500+/month depending on record/search volume; data sent to third-party (DPDPA data localization concern); vendor dependency | Cost; DPDPA data residency risk; vendor lock-in |
| Typesense (self-hosted) | Open source; typo tolerance; fast; simpler than Elasticsearch | Additional ECS service to run and monitor; synchronization pipeline from PostgreSQL; no AWS-managed option; ops burden for 3-person team | Ops complexity for 3 services → 4 services; no managed option |
| PostgreSQL ILIKE / LIKE | Trivially simple; no additional columns | No ranking; full table scan without index; completely unusable at 50K records (P95 >> 500ms) | Performance incompatible with NFR-PE-005 |
| pg_trgm (trigram similarity) | Handles typos; fuzzy matching | Slower than tsvector + GIN at this scale; less relevance tuning; more complex query construction | tsvector GIN is faster at 50K records; pg_trgm better suited for smaller sets or short-string matching |

## Consequences

**Positive:**
- Zero incremental infrastructure cost — FTS runs on already-provisioned RDS instance
- Tight Django ORM integration via `django.contrib.postgres.search` — no external API calls, no synchronization pipeline
- Trigger-based `search_vector` updates are atomic with product saves — search index always consistent with data
- Upgrade path to Elasticsearch requires changing one function (`ProductRepo.search()`) — no application-wide refactoring

**Negative (accepted):**
- No typo tolerance (e.g., "iphne" will not match "iphone") — mitigated by `pg_trgm` optional fallback for very short queries (< 4 characters); accepted at MVP
- No synonym expansion (e.g., "mobile" will not automatically match "smartphone") — acceptable at MVP seller count where sellers manually include both terms in descriptions
- FTS search index update is synchronous with the product write (trigger fires on INSERT/UPDATE) — adds ~5ms to product save operations; acceptable for seller dashboard write paths
- PostgreSQL FTS P95 may degrade above 200,000 products — not an MVP concern; threshold to evaluate Elasticsearch migration documented in ADR

**Performance validation gate:**
- Phase 9 (Testing) must include a load test with 50,000 product records and 100 concurrent search queries
- If P95 search response time exceeds 400ms (approaching 500ms NFR threshold), trigger Elasticsearch evaluation before GA launch
