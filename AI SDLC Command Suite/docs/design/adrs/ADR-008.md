# ADR-008: First-Party Analytics — No Third-Party SDK

**Status:** Accepted
**Date:** 2026-05-14
**Deciders:** Full-stack Lead, Backend Developer, Frontend Developer

---

## Context

ShopNest's PRD Analytics Plan defines 60 analytics events across 12 namespaces required for product iteration, seller performance monitoring, buyer funnel analysis, and payout operational health. The analytics implementation must:

1. Capture all 60 events defined in `docs/prd/PRD-ANALYTICS-PLAN.md`
2. Never block the critical request path — analytics must be fire-and-forget from the client's perspective
3. Keep all user behavioral data within ShopNest's AWS infrastructure (DPDPA 2023 data localization requirement)
4. Satisfy NFR-PE-001 (API P95 < 200ms) — analytics writes must not contribute to response time
5. Respect DPDPA 2023 data minimisation principles — PII collected only where necessary, nulled on account deletion
6. Operate within CON-001 ($2,000/month budget) — no per-event SaaS billing that scales unpredictably
7. Be implementable by a 3-person team without dedicated data engineering (CON-003)

The specific constraint from CLAUDE.md (PRD Phase 3 decision): "First-party analytics only — no third-party SDK. All analytics events captured to internal `analytics_events` PostgreSQL table via `POST /api/v1/analytics/track`. No Mixpanel, Segment, or Amplitude in MVP."

---

## Decision

**First-party analytics: all events captured via `POST /api/v1/analytics/track` to an internal `analytics_events` PostgreSQL table, written asynchronously via Celery.**

**Architecture:**

```
Client (Next.js) → POST /api/v1/analytics/track (202 response, < 50ms)
                      ↓
              Django View (validates schema, enqueues)
                      ↓
              Celery Task: analytics.tasks.write_analytics_event
                      ↓
              PostgreSQL analytics_events table
```

**`analytics_events` table schema:**
```sql
CREATE TABLE analytics_events (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    event_name VARCHAR(100) NOT NULL,
    user_id UUID REFERENCES users_user(id) ON DELETE SET NULL,
    session_id UUID NOT NULL,
    entity_type VARCHAR(50),
    entity_id UUID,
    properties JSONB NOT NULL DEFAULT '{}',
    platform VARCHAR(20) NOT NULL CHECK (platform IN ('web', 'mobile_web')),
    device_type VARCHAR(20) CHECK (device_type IN ('mobile', 'tablet', 'desktop')),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX analytics_events_event_name_idx ON analytics_events (event_name);
CREATE INDEX analytics_events_user_id_idx ON analytics_events (user_id);
CREATE INDEX analytics_events_created_at_idx ON analytics_events (created_at DESC);
CREATE INDEX analytics_events_session_id_idx ON analytics_events (session_id);
```

**Event validation:**
- Django serializer validates `event_name` against a whitelist of 60 defined event names
- `properties` JSONB validated structurally per event type (required keys enforced)
- PII fields in `properties` documented and flagged per PRD-ANALYTICS-PLAN.md
- Unknown events rejected with 400 (prevents unbounded schema drift)

**DPDPA compliance:**
- `user_id` set to `NULL` on account deletion (PostgreSQL `ON DELETE SET NULL` FK)
- PII fields in `properties` (email, name, phone) not written to analytics — only entity IDs
- Seller tax_id, payment card data, bank details never appear in analytics properties
- Analytics events retained 2 years then purged via a scheduled Celery Beat task

**Admin reporting:**
- Django admin custom views for the 4 admin dashboards defined in PRD-ANALYTICS-PLAN.md
- Direct SQL via Django ORM — no BI tool required at MVP
- Data access restricted to `IsAdminUser` permission class

---

## Rationale

**First-party over third-party SDK (DPDPA 2023):**
DPDPA 2023 requires that personal data of Indian users be processed and stored in India. Third-party analytics SaaS (Mixpanel, Amplitude, Segment, PostHog Cloud) routes event data through their own infrastructure — servers in the US or EU — before it can be queried by ShopNest. This creates a cross-border data transfer of behavioral data linked to identifiable Indian users. While some SaaS providers offer India-region data residency, this is either not available in their free/standard tiers or requires enterprise contracts that violate CON-001. First-party analytics with data in ap-south-1 (Mumbai) eliminates the compliance risk entirely.

**PostgreSQL over dedicated time-series DB (CON-001, CON-003):**
At MVP scale (< 1M events/month at 1,000 DAU × 30 events/session), PostgreSQL's JSONB + indexed columns perform well within query time requirements. A dedicated time-series database (InfluxDB, TimescaleDB, AWS Timestream) is justified at 10M+ events/month — not at MVP scale. PostgreSQL is already provisioned; adding a time-series DB adds ~$50–200/month of infrastructure and significant operational complexity for the analytics volume ShopNest will generate in the first 6–12 months.

**Async Celery write (NFR-PE-001):**
`POST /api/v1/analytics/track` returns 202 in < 50ms. The actual database write is enqueued as a Celery task on the `analytics` queue (ADR-006). This completely decouples analytics from the critical API path — a slow or failing analytics write cannot degrade buyer checkout or product browse latency. At 1,000 concurrent users generating analytics events, the `analytics` queue provides natural buffering.

**Event whitelist validation (NFR-MAINT-001):**
Accepting arbitrary event names would cause unbounded schema drift over time — the `analytics_events` table becomes unqueryable without knowing which events exist. Validating against the 60 defined events enforces the contract defined in PRD-ANALYTICS-PLAN.md and prevents frontend bugs from creating phantom events in the database.

## Alternatives Considered

| Option | Pros | Cons | Why Rejected |
|--------|------|------|-------------|
| Mixpanel | Rich funnel analysis; auto-tracking; retention cohorts; no infrastructure | Data stored in Mixpanel's US infrastructure (DPDPA cross-border concern); ~$25–500/month at event volume; vendor lock-in; requires data export for custom queries | DPDPA data residency; cost; data sovereignty |
| Amplitude | Industry-leading product analytics; behavioral cohorts; predictive analytics | Same DPDPA concern as Mixpanel; $0 for < 10M events but no India residency guarantee on free tier; complex export for custom queries | DPDPA risk; querying limitations |
| Segment (Twilio) | Unified event routing; 300+ integrations; structured schema | US infrastructure; DPDPA concern; ~$120/month at 50K MAU; overkill for MVP (one destination: PostgreSQL); added complexity without benefit | DPDPA; cost; unnecessary integration layer |
| PostHog Cloud | Open-source; EU hosting available; feature flags | EU hosting not India; self-hosted adds ECS service overhead; PostHog schema diverges from ShopNest's domain model (60 custom events need mapping) | Not India-resident; self-hosted ops burden |
| PostHog Self-Hosted | Open-source; full control; India-hostable on ECS | Runs ClickHouse + Kafka + multiple services (6+ containers); significant infrastructure overhead; well beyond CON-003 ops capacity for 3-person team | Ops complexity far exceeds benefit at MVP scale |
| AWS Kinesis + Athena | AWS-native; scalable; SQL queries via Athena | Significant setup complexity (Kinesis stream, Firehose, S3 bucket, Glue catalog, Athena); ~$50+/month; engineering time; overkill for MVP event volume | Over-engineering for MVP scale; CON-003 ops burden |
| Google Analytics 4 | Free; rich reporting; product analytics | Data in Google infrastructure (DPDPA concern); GA4 schema mismatches ShopNest's B2B seller events; limited custom event querying without BigQuery; not India-resident | DPDPA; schema mismatch; custom query limitations |

## Consequences

**Positive:**
- 100% data sovereignty — all analytics data in ap-south-1, never leaves ShopNest's AWS account
- Zero incremental SaaS cost — analytics stored in already-provisioned PostgreSQL RDS instance
- Custom query flexibility — any SQL query against `analytics_events` works without API rate limits or export constraints
- Sync with data model — `entity_id` UUID links directly to Products, Orders, Users tables for JOIN queries
- DPDPA `ON DELETE SET NULL` FK ensures user_id purged automatically on account deletion — no manual analytics purge process

**Negative (accepted):**
- No pre-built funnel visualisation, cohort analysis, or retention charts — admin reports are custom Django admin views (sufficient for MVP; post-MVP can add Metabase or Grafana)
- Analytics query performance degrades at very high event volumes (> 50M rows) — 2-year retention purge mitigates; evaluate TimescaleDB migration at 10M+ events/month
- Schema validation rejects unknown events — frontend developers must add new events to the whitelist (a minor coordination overhead, accepted as correct behavior)
- Single PostgreSQL instance for both transactional and analytics data — at MVP scale, analytics queries run off-peak; post-MVP, add a PostgreSQL read replica for analytics queries

**Data retention:**
- Analytics events: 2 years (DPDPA data minimisation compliance)
- Purge implemented as monthly Celery Beat job: `analytics.tasks.purge_old_events()`
- Financial records (`orders`, `payments`, `settlements`) retain for 7 years per BR-011 — not purged by this task
