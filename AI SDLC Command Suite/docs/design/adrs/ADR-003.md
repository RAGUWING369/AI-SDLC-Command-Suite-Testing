# ADR-003: PostgreSQL 16 as Primary Database

**Status:** Accepted
**Date:** 2026-05-14
**Deciders:** Full-stack Lead, Backend Developer

---

## Context

ShopNest requires a primary persistent data store for 19 entities (see DATA-MODEL.md), including relational order→sub-order→line-item hierarchies, JSONB for delivery addresses and state snapshots, full-text search across product names and descriptions (NFR-PE-005), atomic stock decrement under concurrent checkout (BR-008), financial record retention for 7 years (BR-011), and AES-256 encryption at rest (NFR-SEC-002).

The database must satisfy:
- NFR-PE-005: Product search P95 < 500ms at ≤50,000 products
- NFR-PE-008: DB query P95 < 50ms
- NFR-REL-003: RPO < 1 hour (requires 1-hour automated backup)
- NFR-REL-001: 99.9% uptime (requires Multi-AZ failover)
- NFR-SEC-002: AES-256 encryption at rest
- BR-008: Atomic stock decrement at payment.captured (prevents overselling)
- BR-011: 7-year financial record retention

---

## Decision

**PostgreSQL 16 on AWS RDS, instance class db.t3.small, Multi-AZ enabled, with 1-hour automated backups and 35-day PITR window.**

Key PostgreSQL-specific features used:
1. **TSVECTOR + GIN index** for product full-text search (ADR-007)
2. **JSONB** for `delivery_address`, `before_state`, and `after_state` in Orders and AuditLog
3. **`gen_random_uuid()`** as database-level UUID default for all primary keys
4. **`SELECT ... FOR UPDATE`** for atomic stock decrement (`stock_quantity = stock_quantity - qty WHERE stock_quantity >= qty`)
5. **`CHECK` constraints** enforcing `stock_quantity >= 0`, `price_paise >= 100`, `quantity >= 1`
6. **`TIMESTAMPTZ`** (not `TIMESTAMP`) for all datetime fields — timezone-aware; all times stored in UTC

---

## Rationale

**Full-text search (NFR-PE-005):** PostgreSQL's native FTS with a GIN-indexed `tsvector` column on `(name, description)` delivers P95 search queries in < 100ms at 50,000 products (based on PostgreSQL FTS benchmarks at this record count). This avoids the operational complexity of Elasticsearch (separate service, separate cluster, synchronization lag) at MVP scale. If search quality/volume demands Elasticsearch post-MVP, the `search_vector` column provides a clean upgrade path without data model changes.

**JSONB (NFR-PE-008):** `delivery_address` is stored as JSONB because the structure is fixed at the application layer but PostgreSQL JSONB enables GIN indexing on address fields without schema changes. `before_state`/`after_state` in AuditLog stores arbitrary entity snapshots without requiring a separate schema per entity type.

**Atomic stock decrement (BR-008):** PostgreSQL row-level locking (`SELECT FOR UPDATE SKIP LOCKED`) enables the checkout service to atomically decrement stock and reject the transaction if stock is insufficient — preventing the overselling race condition that would occur with application-layer stock checks followed by a separate update.

**Multi-AZ + PITR (NFR-REL-001 + NFR-REL-003):** AWS RDS Multi-AZ provides automatic failover to a standby instance in a different AZ in < 60 seconds, enabling ≥99.9% uptime. Automated snapshots every 1 hour satisfy RPO < 1 hour. PITR to any second within the 35-day window provides additional protection against accidental data corruption.

**RDS encryption (NFR-SEC-002):** AWS RDS encryption at rest using AWS KMS with AES-256 covers all data at the storage layer. This satisfies the NFR baseline. `PayoutDetails.account_number` receives additional application-layer AES-256 encryption (defense in depth) because bank account numbers require a higher protection level than generic storage encryption.

**db.t3.small instance sizing:** At MVP scale (≤100 sellers, ≤1,000 concurrent users), 2 vCPU and 2GB RAM is sufficient. max_connections ≈ 200 (computed from PostgreSQL formula); 2–10 ECS tasks × 10 connections/worker = 20–100 connections — within limits with 2× headroom. Upgrade path: db.t3.medium at >150 sellers (adds 2GB RAM, doubles connection capacity).

## Alternatives Considered

| Option | Pros | Cons | Why Rejected |
|--------|------|------|-------------|
| MySQL 8.0 | Widely used; RDS available; good performance | Inferior FTS (FULLTEXT index is simpler than PostgreSQL's tsvector/tsquery + ranking); JSONB not natively available (JSON supported but no GIN indexing); UUID PK less mature (requires `CHAR(36)` not native UUID type) | FTS quality insufficient for NFR-PE-005; JSONB requirements |
| MongoDB | Flexible schema; BSON documents; horizontal sharding | Document model poor fit for relational Order→SubOrder→LineItem hierarchy; ACID transactions across documents require complex configuration; team proficiency is relational not document; Django ORM does not natively support MongoDB | Schema mismatch; ACID complexity; ORM incompatibility |
| SQLite | Zero operational overhead; built into Python | Not suitable for multi-process ECS environment (file locking); not production-grade for concurrent writes at 1,000 users | Cannot run in distributed ECS environment |
| DynamoDB | AWS-native; infinite scale; serverless | No ACID transactions for stock decrement (BR-008 requires atomic operations); no native FTS; no Django ORM support without complex adapters; hourly cost unpredictable at query volume | ACID requirements incompatible |

---

## Consequences

**Positive:**
- PostgreSQL FTS eliminates the need for a separate search service at MVP scale (saves ~$200/month Elasticsearch cost and significant operational complexity)
- Django ORM fully supports all PostgreSQL-specific features (JSONB, UUID, FTS via `SearchVector`, `SearchQuery`, `SearchRank`)
- AWS RDS provides automatic Multi-AZ failover, backups, and patching — no DBA required (important for 3-person team)
- `CHECK` constraints at the database level provide a second line of defense against data integrity bugs

**Negative (accepted):**
- db.t3.small may need upgrading if query complexity grows beyond estimated load — monitored via RDS Performance Insights
- PostgreSQL FTS has lower recall/relevance than Elasticsearch for complex search queries (stemming, synonyms, typo tolerance) — acceptable at MVP; Elasticsearch planned for post-MVP if search NPS < target
- Multi-AZ doubles RDS cost (~$70/month for db.t3.small Multi-AZ vs. ~$35 single-AZ) — required for NFR-REL-001, within CON-001 budget

**Future implications:**
- When Elasticsearch is added post-MVP, the `search_vector` column can be removed and the `ProductRepo.search()` method updated without data model changes elsewhere
- Read replicas can be added to PostgreSQL for analytics/reporting queries without application changes
