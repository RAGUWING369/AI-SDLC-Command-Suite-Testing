# ADR-004: RS256 JWT Authentication Strategy

**Status:** Accepted
**Date:** 2026-05-14
**Deciders:** Full-stack Lead, Backend Developer

---

## Context

ShopNest has three distinct user roles — Buyer, Seller, and Platform Admin — each requiring access to different API endpoints. Seller access is further gated by subscription status (FR-AUTH-007). Guest checkout requires partial unauthenticated access to protected resources (cart and checkout endpoints).

Authentication must satisfy:
- NFR-SEC-003: RS256-signed JWT; access token 24h; refresh token 30d
- NFR-SEC-004: bcrypt cost factor ≥12 for password storage
- NFR-SEC-010: Admin endpoints return 403 for non-admin roles
- NFR-SEC-005: Multi-tenant data isolation (seller_id scoping)
- FR-AUTH-006: RBAC with three roles (Buyer, Seller, Admin)
- FR-AUTH-007: Seller dashboard blocked if subscription not Active
- FR-AUTH-010: Refresh token invalidated on logout

---

## Decision

**RS256 JWT with asymmetric RSA-2048 key pair, implemented via `djangorestframework-simplejwt` with bcrypt password hashing.**

**Token specifications:**
- Access token: RS256-signed JWT, expires 24 hours, contains `user_id`, `role`, `seller_status` (for Sellers), `email`
- Refresh token: RS256-signed JWT, expires 30 days, used only to obtain new access tokens
- Refresh token denylist: stored in Redis on logout; checked before issuing new access token

**Key storage:**
- RS256 private key: AWS Secrets Manager (fetched at container startup, cached in memory)
- RS256 public key: Served at `GET /.well-known/jwks.json` for future service-to-service validation

**Password hashing:**
- Django `BCryptSHA256PasswordHasher` with `BCRYPT_ROUNDS = 12`
- Hash format: `$2b$12$...` verified in Phase 9 security tests

**RBAC enforcement:**
- DRF permission classes: `IsBuyerUser`, `IsSellerUser`, `IsAdminUser`, `IsSellerWithActiveSubscription`
- Classes applied at ViewSet level (not controller-level ad-hoc checks)
- Middleware extracts and validates JWT on every authenticated request; role from JWT claims drives permission class selection

**Guest checkout:**
- Cart and checkout endpoints accept requests with no JWT
- Session identified by `X-Session-ID` header (UUID set by backend on first cart interaction, returned as HTTP-only cookie)
- Guest order tracking authenticated via HMAC-SHA256 token in URL (A-02-010)

---

## Rationale

**RS256 over HS256 (NFR-SEC-003):** RS256 uses an asymmetric key pair — the private key signs tokens, the public key verifies them. HS256 uses a single shared secret for both signing and verification. In a multi-service architecture (even at MVP with frontend + backend + Celery), RS256 allows any service to verify tokens using only the public key without possessing the signing secret. This is more secure: compromising the Next.js frontend cannot expose the token signing key. The public key can be safely published at `.well-known/jwks.json` for future service expansion.

**JWT over session-based auth:** Sessions require server-side storage (Redis or DB) and a session lookup on every request — adds a Redis round-trip (~5ms) per API call. JWT is stateless — token validation is a local cryptographic operation. At 1,000 concurrent users and P95 < 200ms target, eliminating the session lookup per request preserves ~5ms of headroom. Sessions would also complicate Celery task auth (tasks don't have HTTP sessions).

**bcrypt cost 12 (NFR-SEC-004):** bcrypt cost factor 12 takes ~250ms per hash on modern hardware — sufficient to make brute-force attacks computationally expensive while being fast enough for login throughput at MVP scale (100 req/s login rate is theoretically possible but highly unlikely at 100 sellers + 1,000 buyers; real login rate is <<1 req/s).

**Token denylist in Redis (FR-AUTH-010):** Refresh token invalidation on logout is implemented by adding the token JTI (JWT ID) to a Redis set with the token's remaining TTL as expiry. This is a compromise between full statelessness (no denylist — cannot revoke tokens) and full session-based auth (stateful lookup on every request). Only the refresh endpoint checks the denylist; access token validation remains purely stateless.

**djangorestframework-simplejwt:** Provides RS256 support, DRF integration, token refresh endpoint, and token denylist middleware out of the box. Reduces custom auth code to near zero.

## Alternatives Considered

| Option | Pros | Cons | Why Rejected |
|--------|------|------|-------------|
| HS256 JWT | Simpler (one secret key) | Shared secret must be distributed to any service that verifies tokens — higher compromise risk; violates security principle of least knowledge | Security posture inferior to RS256 for multi-component system |
| Session-based auth (Django sessions) | Simpler to implement; easy revocation | Server-side session lookup on every request adds Redis round-trip (~5ms); complicates Celery task auth; scales worse under high concurrency | Latency cost per request; Celery integration complexity |
| OAuth 2.0 + PKCE (social login) | Standard for third-party login flows | Adds external identity provider dependency; complicates seller onboarding; ShopNest uses its own email/password auth | Unnecessary complexity for email/password-only auth at MVP |
| Magic link (email-based, no password) | No password storage vulnerability | Poor UX for sellers (frequent dashboard access); not familiar to Indian SME sellers | UX regression; user expectation mismatch |
| API Keys (seller dashboard) | Simple to implement | No role granularity; no expiry mechanism; harder to revoke individual sessions | RBAC requirements cannot be satisfied with API keys alone |

---

## Consequences

**Positive:**
- Stateless access token verification — no Redis lookup per API request (saves ~5ms/request)
- JWT claims carry `role` and `seller_status` — RBAC and subscription gate checks are pure Python operations on the decoded claim (no DB round-trip per request)
- RS256 public key can be published for future internal service federation without sharing signing credentials
- simplejwt handles token lifecycle, refresh, and denylist — minimal custom auth code in Phase 7

**Negative (accepted):**
- Access tokens are irrevocable within their 24-hour lifetime (if stolen, attacker has access until expiry) — mitigated by short 24h window, HTTPS-only, HTTP-only refresh token cookie
- RSA-2048 key pair must be rotated periodically — rotation policy: annually, or immediately on suspected compromise; new key pair generated in Secrets Manager, JWKS endpoint updated
- Refresh token denylist in Redis — if Redis fails during logout, the logout appears successful but the refresh token may not be fully revoked until Redis recovers (acceptable UX risk; Redis is highly available via ElastiCache)

**Future implications:**
- When ShopNest adds mobile apps (post-MVP), the same JWT auth strategy works without changes
- When a microservice is extracted post-MVP (e.g., payout service), it can verify ShopNest JWTs using the public JWKS endpoint without needing the signing key
