# ADR-006: Celery + Redis for Async Task Processing

**Status:** Accepted
**Date:** 2026-05-14
**Deciders:** Full-stack Lead, Backend Developer

---

## Context

ShopNest requires an asynchronous task processing layer for operations that must not block the HTTP request-response cycle:

1. **Weekly payout batch job** (BR-006): Every Monday 09:00 IST, process all `SettlementLedgerEntry` records with `status=PENDING`, aggregate by seller, call Razorpay Payouts API, create `Payout` records. At 100 sellers, this is a long-running sequential process (potentially 30–120 seconds).
2. **Async email dispatch** (NFR-REL-006): Order confirmation, subscription invoice, payout notification emails via AWS SES — must not add latency to the checkout critical path.
3. **Async analytics writes** (NFR-PE-001, PRD Analytics Plan): `POST /api/v1/analytics/track` must respond in < 50ms; actual `analytics_events` DB write happens asynchronously.
4. **Async audit log writes**: `AuditLog` entries written after state-changing operations; must not block the transaction that triggers them.
5. **Razorpay webhook processing**: HMAC validation completes synchronously; downstream processing (stock decrement, SubOrder creation, email trigger) dispatched to Celery to ensure webhook returns 200 within Razorpay's 5-second timeout.

The async framework must satisfy:
- NFR-REL-006: Email delivery within 30 seconds of trigger event
- NFR-PE-001: API P95 < 200ms (async operations must not contribute to response time)
- BR-006: Weekly payout executed reliably with retry on transient Razorpay API failure
- CON-007: Single Django codebase — async tasks must share Django ORM, models, and settings
- CON-001: Within $2,000/month budget (Redis is already in the stack for cart/cache)

---

## Decision

**Celery 5.x with Redis 7.x as the message broker and result backend, with Celery Beat for scheduled task execution.**

**Task definitions:**

| Task | Queue | Retry Policy | Schedule |
|------|-------|--------------|----------|
| `payments.tasks.process_weekly_payouts` | `payouts` | 3 retries, 5min backoff | Celery Beat — Monday 09:00 IST |
| `notifications.tasks.send_order_confirmation_email` | `email` | 3 retries, 60s backoff | On-demand (checkout webhook) |
| `notifications.tasks.send_subscription_invoice_email` | `email` | 3 retries, 60s backoff | On-demand (subscription created) |
| `notifications.tasks.send_payout_notification_email` | `email` | 3 retries, 60s backoff | On-demand (payout processed) |
| `analytics.tasks.write_analytics_event` | `analytics` | 1 retry, 10s backoff | On-demand (every track call) |
| `orders.tasks.write_audit_log` | `default` | 2 retries, 30s backoff | On-demand (state changes) |

**Queue configuration:**
- `payouts` queue: consumed by a dedicated Celery worker container (ensures payout job cannot be delayed by email backlog)
- `email` queue: consumed by the default Celery worker
- `analytics` queue: consumed by the default Celery worker
- `default` queue: all other tasks

**Celery Beat scheduler:**
- `django-celery-beat` with database scheduler (schedule stored in PostgreSQL — survives container restarts)
- Payout job scheduled as `crontab(hour=3, minute=30, day_of_week=1)` UTC → 09:00 IST (UTC+5:30)

**Broker + Result Backend:**
- Broker: Redis 7.x (same ElastiCache instance as cart cache, separate DB index `db=1` for Celery)
- Result backend: Redis (task results retained 1 hour TTL — not used for business logic, only health monitoring)
- No separate SQS queue — Redis already provisioned, adding SQS adds cost and complexity

**ECS deployment:**
- Celery worker runs as a separate ECS service (`shopnest-celery`) using the same Docker image as Django API, different `CMD`: `celery -A shopnest worker -Q default,email,analytics,payouts -c 4`
- Celery Beat runs as a separate ECS service (`shopnest-celery-beat`) with a single task (min 1, max 1) to prevent duplicate scheduled job execution

---

## Rationale

**Celery over Django Q (CON-007, NFR-REL-006):**
Django Q is a lighter alternative built for Django, but its task scheduling (via `Schedule` model) is less mature than Celery Beat, has fewer production deployments at scale, and lacks the `django-celery-beat` database scheduler integration. Celery has a significantly larger ecosystem, better monitoring tooling (Flower, CloudWatch metric integration), and Django REST Framework documentation assumes Celery for async patterns. At ShopNest's scale, Celery's additional features are operationally valuable.

**Celery over RQ (Redis Queue) (NFR-REL-006, BR-006):**
RQ is simpler than Celery but lacks built-in periodic task scheduling — the weekly payout job would require a separate cron mechanism (ECS scheduled tasks or crontab in the container). RQ also lacks multi-queue routing with priority queues, which ShopNest needs to isolate the payout queue from email backlog. Celery Beat + queue routing covers both requirements natively.

**Redis broker over AWS SQS (CON-001):**
Redis is already provisioned in the stack (ElastiCache cache.t3.micro) for cart data and product cache. Using Redis as the Celery broker adds zero incremental infrastructure cost — just a separate Redis DB index. AWS SQS would add a new managed service (~$0.40/million messages, plus data transfer), additional IAM configuration, and SQS-specific Celery backend (`celery-sqs`) which has known limitations (no task result backend, no Celery Beat native support). Redis is the simpler, cost-free choice given ElastiCache is already in the stack.

**Separate Celery Beat container (BR-006 reliability):**
Celery Beat must run as exactly one instance to prevent duplicate job scheduling. ECS Fargate service with `desiredCount=1` and `minimumHealthyPercent=0` (allows single-task rolling updates) ensures exactly one Beat instance runs. The alternative (running Beat inside the worker container) risks multiple Beat instances if the worker scales horizontally.

**`django-celery-beat` database scheduler (CON-007):**
Storing Beat schedules in PostgreSQL (not the default file-based clock store) means schedules survive container restarts and can be managed via Django admin. This eliminates "beat lost its schedule state" incidents that occur with the default file-based approach on stateless ECS containers.

## Alternatives Considered

| Option | Pros | Cons | Why Rejected |
|--------|------|------|-------------|
| Django Q | Pure Django; simpler setup; database broker option | Less mature scheduling; fewer production examples; limited queue routing; smaller ecosystem | Missing features for payout scheduling + queue isolation |
| RQ (Redis Queue) | Simple; Redis-native; easy Django integration | No built-in periodic scheduling; no multi-queue routing priority; Beat equivalent requires separate cron | Weekly payout requires periodic scheduling |
| AWS SQS + Lambda | Fully managed; infinite scale; no broker management | Lambda 15-min limit blocks payout job; cold starts add latency; SQS adds cost; not free given Redis already available | Lambda execution limit; CON-001 (unnecessary added cost) |
| AWS SQS + ECS worker | Avoids Lambda limit; fully managed queue | Additional IAM complexity; SQS cost; no Celery Beat equivalent; significant Celery-equivalent code to write | Added cost and complexity vs. Redis already in stack |
| Celery + RabbitMQ | More robust broker than Redis for very high throughput | Additional managed service (no AWS-managed RabbitMQ equivalent; Amazon MQ is expensive); Redis already in stack; ShopNest volume doesn't require RabbitMQ's throughput guarantees | Over-engineering; additional cost; Redis sufficient at MVP scale |

## Consequences

**Positive:**
- Same Django ORM, models, and settings used in Celery tasks — no code duplication or cross-service API calls
- Celery Beat in PostgreSQL survives ECS container restarts — no missed payout jobs
- Queue isolation (`payouts` queue) ensures payout batch never delayed by email or analytics backlog
- Flower (Celery monitoring dashboard) deployable as an internal ECS service for task health visibility
- Built-in retry with exponential backoff handles transient Razorpay API errors in payout task

**Negative (accepted):**
- Redis as Celery broker creates a dependency chain: if ElastiCache Redis fails, both cart and Celery broker are unavailable — mitigated by ElastiCache Multi-AZ replication (automatic failover < 60s)
- Celery worker ECS service adds ~$9/month to infrastructure cost (0.5 vCPU / 1GB RAM) — within CON-001 budget; already included in ADR-005 cost estimate
- Celery task failures require CloudWatch log monitoring to detect — mitigation: CloudWatch alarm on Celery worker DLQ (dead letter queue pattern via Redis key expiry)
- `django-celery-beat` requires the Beat container to have DB access — same PostgreSQL connection pool considerations as API container

**Future implications:**
- When ShopNest extracts a Payout microservice post-MVP, the Celery task queue interface provides a clean async boundary — the extracted service can consume from the same `payouts` Redis queue with no API contract change
- Analytics queue can be migrated to a dedicated Redis cluster if analytics write volume exceeds ElastiCache capacity
