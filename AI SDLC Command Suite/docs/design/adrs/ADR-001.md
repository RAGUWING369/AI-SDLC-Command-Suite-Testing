# ADR-001: Modular Django Monolith Architecture Pattern

**Status:** Accepted
**Date:** 2026-05-14
**Deciders:** Full-stack Lead, Backend Developer, Frontend Developer

---

## Context

ShopNest must be delivered as a production-ready MVP by 2026-10-31, built by a team of 3 developers. The system must support ≥1,000 concurrent users, process payments via Razorpay, manage multi-vendor seller data isolation, and handle weekly automated payout batches. The team has no dedicated DevOps resource.

An architectural pattern must be selected before Phase 7 implementation begins. The pattern determines the deployment topology, service boundaries, inter-component communication, operational complexity, and long-term scalability ceiling.

Relevant constraints from CLAUDE.md and REQUIREMENTS.md:
- CON-003: 3 developers, no dedicated DevOps or QA
- CON-007: Microservices architecture is explicitly excluded
- CON-002: MVP deadline 2026-10-31 (~24 weeks from project start)
- NFR-PE-006: ≥1,000 concurrent users without degradation
- NFR-REL-001: 99.9% monthly uptime

---

## Decision

**ShopNest will be implemented as a Modular Django Monolith.**

A single Django project containing seven internal apps — `users`, `sellers`, `products`, `orders`, `cart`, `payments`, `analytics` — each with strong internal boundaries (no direct model imports across apps except through defined service interfaces), deployed as a single ECS Fargate container image alongside a separate Celery worker container (same image, different CMD) and a separate Next.js frontend container.

The monolith is modular: each Django app owns its models, views, serializers, services, and tests. Cross-app communication occurs through service layer calls, not direct ORM imports. This preserves the option to extract individual apps as microservices post-MVP.

---

## Rationale

**Why not microservices?**
- CON-007 explicitly excludes microservices
- A 3-person team operating microservices would spend 40–60% of sprint capacity on inter-service communication, distributed tracing, separate CI pipelines, and service discovery — leaving insufficient time for feature delivery
- Microservices for ≤1,000 concurrent users and ≤100 sellers is over-engineering; the operational cost exceeds the scaling benefit at this scale

**Why not a simple (unmodular) monolith?**
- An unstructured monolith creates coupling that makes future service extraction expensive (the "Big Ball of Mud" anti-pattern)
- Strong app boundaries give the Implementation Agent (Phase 7) clear code ownership per developer
- Module boundaries enforce NFR-SEC-005 (multi-tenant data isolation) at the code structure level

**Why not serverless?**
- Lambda 15-minute max execution blocks the weekly payout Celery job (which must process 100+ sellers sequentially)
- Lambda cold starts are incompatible with NFR-PE-001 (P95 < 200ms API latency)
- Razorpay webhook processing requires persistent process (HMAC validation + DB write + Celery enqueue must complete in < 5s)

---

## Alternatives Considered

| Option | Pros | Cons | Why Rejected |
|--------|------|------|-------------|
| Microservices | Independent scaling per service; team autonomy; technology heterogeneity | 3-person team cannot sustain distributed system ops; 6-month delay vs. monolith; explicit CON-007 exclusion | CON-007; team constraint |
| Serverless (Lambda + API Gateway) | Zero server management; pay-per-invocation | Lambda cold starts violate NFR-PE-001; 15min limit blocks payout jobs; complex local dev | Performance NFRs incompatible |
| Hybrid (monolith + extracted payout service) | Payout service independently deployable | Adds inter-service auth complexity; payout is weekly batch — doesn't justify extraction at MVP | Premature optimization; adds ops burden |
| Simple (unmodular) monolith | Simplest possible structure | Creates coupling; blocks post-MVP service extraction; code ownership unclear | Technical debt accumulation |

---

## Consequences

**Positive:**
- Entire team can deliver features without cross-service coordination overhead
- Single deployment unit — ECS rolling update deploys all changes atomically
- Local development uses `docker-compose up` — no service mesh or registry required
- Django ORM enforces multi-tenant isolation across the entire data layer uniformly
- Feature flag pattern (env vars) works trivially in a monolith — no cross-service flag synchronization

**Negative (accepted trade-offs):**
- Horizontal scaling scales the entire application, not individual bottlenecks — acceptable at ≤1,000 users; post-MVP growth to >10,000 users will require service extraction
- A bug in one app can potentially affect all apps in the same process — mitigated by Python exception handling, DRF error middleware, and 80% test coverage gate
- Database connection pool is shared across all apps — mitigated by connection pool sizing (10 connections per Gunicorn worker) and RDS max_connections headroom

**Future implications:**
- The modular structure makes post-MVP service extraction straightforward: extract one Django app at a time, starting with `payments` (highest independent scaling need) or `analytics` (most isolated by design)
- When the team grows beyond 8 developers, individual apps can be owned by separate sub-teams without codebase conflicts
